# Commit-mined candidates for a discriminating screening roster (2026-08-16)

## Why this exists

Feasibility batch 3 accepted 27/27 controlled runs with zero escalations. Ceiling
effects at that level make cost-per-accepted-outcome uninformative: if every
configuration passes, quality cannot separate them and QA-ECST collapses to raw
cost. This register mines candidate tasks hard enough that acceptance is expected
to vary by configuration, so the escalation probe required by SPEC §5.1 has
something to bite on.

Sourcing follows SPEC §5.1 and `tasks/WORKLOAD-SELECTION.md` §4: the agent starts
at the merge commit's parent (N−1) and must reproduce the effect of the merged PR
(N); the PR's own tests supply the gate and the pre-modification failure proof.

`tasks/proposals/2026-08-diversed-coding-tasks.md` was used as **class briefs only**.
Its declared SHAs are fabricated (0/15 resolved at the 2026-08-15 verification) and
one of its repositories (`HKUDS/Spider2`) does not exist — the real Spider 2.0 repo
is `xlang-ai/Spider2`. No commit, path, or repository from that file is carried
forward here.

## Verification method

Python `urllib.request` against `api.github.com` with a `User-Agent` header and a
bearer token (the token raises the rate limit from 60/h to 5000/h; it changes
nothing about what is read — all endpoints are public). For each candidate:

1. `GET /repos/{owner}/{repo}/pulls/{n}` → confirm `merged: true`, read
   `merge_commit_sha` (**N**).
2. `GET /repos/{owner}/{repo}/commits/{N}` → confirm N resolves; read `parents`.
3. `GET /repos/{owner}/{repo}/commits/{parents[0]}` → confirm N−1 resolves.
4. `GET /repos/{owner}/{repo}/pulls/{n}/files` → per-file additions/deletions and
   patch text, for the difficulty rationale.
5. `GET /repos/{owner}/{repo}/contents/pyproject.toml|requirements_dev.txt` at N−1 →
   dependency and build-system evidence for the hermeticity assessment.

**Result: 16 of 16 SHAs resolved (8 merge commits + 8 parents). All eight PRs are
merged. All eight merges are squash merges (exactly one parent), so `parents[0]` is
unambiguously the agent's start point.**

## Cross-cutting notes

- **All eight repositories are permissively licensed** (MIT ×7, Apache-2.0 ×1) and
  permit clone, modify, run, and redistribution of derived fixtures — criterion 4 of
  `tasks/WORKLOAD-SELECTION.md` §1.
- **All eight gates are hermetic.** Every dependency resolves to a Python wheel or an
  npm package installed at *image build* time; the gate itself runs `--network=none`.
  None of the eight needs a live warehouse, a cloud credential, or an outbound socket
  — which is exactly the failure mode that disqualified proposal tasks 4 and 10.
- **Contamination tiers are proposals.** `post_cutoff` is model-relative
  (`tasks/WORKLOAD-SELECTION.md` §2): each candidate's basis is its merge date, and
  the tier must be confirmed against each subject's *declared* cutoff at
  CP-SCREEN-PREREG. Where a subject's cutoff turns out to be later than the merge
  date, the visibility-based fallback tier in the table applies instead. Tiers are
  never revised after results.
- **Class-claim coverage** (`tasks/WORKLOAD-SELECTION.md` §3): complex_bugfix would be
  covered by two or three *different repositories* (sqlglot, anyio, zarr), and the
  corroborating tasks fall in `obscure`/`post_cutoff` — so a class-level promotion is
  not blocked by the contamination rule.
- **Escalation probe** (SPEC §5.1): C5 is the recommended designation — highest
  volume, strictest parity constraint, and an anti-no-op structural check that a
  degraded submission cannot dodge. C1 is the fallback (a four-site invariant that a
  local patch cannot satisfy). The prediction must be recorded at CP-SCREEN-PREREG
  before any run, and published whichever way it lands.
- **Nothing here has been executed.** Pre-modification failure proofs are derived from
  the PRs' own diffs and are stated as *expected*; each becomes a measured fact only
  when the task clears ten-point validation in a clean container.
